## 2. Executive summary

| Severity | Findings |
|---|---|
| Critical | 0 |
| High | 0 |
| Medium | 2 |
| Low | 5 |
| Informational | 2 |

The three most urgent issues:

1. **F-01:** the subscription form is limited only per IP address, so an attacker who rotates addresses can make the site send confirmation emails to any number of third parties and use up the daily Brevo quota that password reset and security emails also depend on.
2. **F-02:** the 2FA challenge throttle is keyed on the pending login and the IP address together, so an attacker who knows the password and rotates addresses gets unlimited guesses at the 6-digit code.
3. **F-05:** the application sets no security headers (CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy`, frame protection), and no production web server configuration exists yet to add them.

Overall risk: no way was found for an unauthenticated visitor to read data, run script in a reader's browser or reach the admin panel, and the article sanitizer resisted every bypass tried. The real exposure is abuse of the two IP-keyed throttles and hardening that the production setup has not done yet. No dependency has a known vulnerability.

## 5. Findings detail

### F-01: Subscription throttle is per IP only: confirmation email flooding and mail quota exhaustion

**Severity:** Medium, CVSS 6.5 (`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:L`)

**Location:** `app/Providers/AppServiceProvider.php:46-48` (`subscription` rate limiter), `routes/web.php:52-54` (`subscriptions.store`), `app/Http/Controllers/SubscriptionController.php:84-112` (`subscribe()`), `app/Support/DnsResolver.php:17`.

**Description:** `POST /abonnement` accepts any email address on a domain that has an MX, A or AAAA record and queues a confirmation email to it. The only limits are 5 requests per hour per exact IP address, one email per address per 10 minutes, and a honeypot field. There is no limit across addresses or across the whole site, and an IPv6 client controls at least a /64, so each new address in it gets a fresh allowance.

**Attack path:**

1. The attacker prepares a list of real email addresses (victims, or addresses on domains they do not own).
2. From rotating IP addresses (one IPv6 /64, or a proxy pool), they send `POST /abonnement` with `email=<victim>` and an empty `website` field, 5 per address per hour.
3. Each request passes `SubscribeRequest`, creates a pending `subscriptions` row and queues `ConfirmSubscription`.
4. The queue worker sends each email through Brevo, from `contact@randy-donny.com`.
5. `.env.example` states that the Brevo plan sends 300 emails a day, transactional ones included, and that the newsletter may take 250 of them. After 50 to 300 forged subscriptions, Brevo refuses further mail for the day.

**Evidence:**

```php
RateLimiter::for('subscription', fn (Request $request): Limit => Limit::perHour(5)
    ->by($request->ip())
```

Local test, 6 requests from each of three neighbouring IPv6 addresses, a different email each time: requests 1 to 5 from every address were accepted, and the test ended with `rows=15`.

**Impact:** Third parties receive unsolicited email from the blog's domain, which harms its sender reputation and may get the Brevo account suspended. With the quota used up, password reset links, new-device alerts, login email confirmations and that day's newsletter are not delivered. Each request also runs up to three blocking DNS lookups (`checkdnsrr`) in an Octane worker, so a batch of addresses on slow-to-resolve domains can hold the workers (this last point was not measured).

**Remediation:**

- Add a site-wide cap next to the per-IP one, and key IPv6 clients on their /64:

```php
RateLimiter::for('subscription', fn (Request $request): array => [
    Limit::perHour(5)->by(self::clientNetwork($request->ip()))->response($tooMany),
    Limit::perDay(100)->by('subscription-global')->response($tooMany),
]);
```

- Add a challenge that costs the attacker something: Cloudflare Turnstile or hCaptcha on the form, checked server-side before the DNS lookup.
- Keep transactional mail away from the shared quota (a paid Brevo plan, or a second sender for security emails).
- Regression tests: the 6th request from a second address of the same /64 is refused; request number 101 of the day is refused whatever its IP.

**References:** CWE-770 (Allocation of Resources Without Limits or Throttling), CWE-799, OWASP Top 10 A04 Insecure Design, OWASP ASVS V11.1 (business logic limits), OWASP Automated Threats OAT-021.

### F-02: 2FA challenge throttle can be bypassed by changing IP address

**Severity:** Medium, CVSS 6.8 (`CVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:N`). `PR:L` stands for the precondition that the attacker already knows the account password.

**Location:** `app/Providers/FortifyServiceProvider.php:96-97` (`admin-two-factor` rate limiter), `routes/admin.php:26-28` (`two-factor.login.store`).

**Description:** The 2FA challenge allows 5 codes a minute, counted per pending login and IP address together. The pending login (`login.id`) lives in the session and stays valid when the client's address changes, so every new address gets 5 more guesses against the same challenge. Fortify itself keeps no count of failed codes.

**Attack path:**

1. The attacker obtains the admin password (phishing, reuse, a leak).
2. They post it to `/admin/connexion`. Fortify stores `login.id` in the session and redirects to `/admin/deux-facteurs`.
3. With that session cookie, they post `code=000000`, `000001`, … to `/admin/deux-facteurs`, 5 per source address, and move to the next address when the form answers « Trop de tentatives ».
4. A code is valid for its 30-second window and the neighbouring ones, so each guess succeeds with a probability of about 3 in 1,000,000. About 330,000 guesses are expected, which is about two hours at 50 requests a second.
5. On the valid code, Fortify logs the session in as the administrator.

**Evidence:**

```php
RateLimiter::for('admin-two-factor', fn (Request $request): Limit => Limit::perMinute(5)
    ->by($request->session()->get('login.id').'|'.$request->ip())
```

Local test, same session and same `login.id`, 7 wrong codes from each of four addresses: attempts 1 to 5 from every address answered « Ce code est incorrect. », and only attempts 6 and 7 answered « Trop de tentatives ».

**Impact:** The second factor does not protect an account whose password is known. The attacker gains the full admin panel: the subscriber list (email addresses), every article and newsletter, and the ability to send email to all subscribers.

**Remediation:** Count failures per account, not per address, and add a slower second limit so a short pause does not reset the count:

```php
RateLimiter::for('admin-two-factor', fn (Request $request): array => [
    Limit::perMinute(5)->by('2fa-minute|'.$request->session()->get('login.id')),
    Limit::perHour(20)->by('2fa-hour|'.$request->session()->get('login.id')),
]);
```

This lets someone who knows the password delay the owner's own challenge, which is the lesser harm, and the existing `NewDeviceLogin` and login history already tell the owner. Also send a security alert after repeated failed challenges. Regression test: after 5 wrong codes, a 6th from another `REMOTE_ADDR` with the same session is refused.

**References:** CWE-307 (Improper Restriction of Excessive Authentication Attempts), OWASP Top 10 A07 Identification and Authentication Failures, OWASP ASVS V6.3 and V6.6 (rate limiting of authentication and out-of-band factors), [Laravel rate limiting](https://laravel.com/docs/13.x/rate-limiting).

### F-03: Login throttle is per email and IP only, with no account-level limit

**Severity:** Low, CVSS 3.7 (`CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N`). The score is kept low because the production password policy (12 characters, mixed, checked against breach lists) makes online guessing impractical; a weak or reused password would raise it.

**Location:** `config/fortify.php:129` (`'login' => null`), `routes/admin.php:23` (`login.store`), `vendor/laravel/fortify/src/LoginRateLimiter.php:90-93`.

**Description:** With no custom limiter, Fortify throttles logins at 5 failures a minute per email and IP pair. Nothing limits the total number of failures against one account, so an attacker who rotates addresses can guess passwords without ever being slowed. 2FA is optional, and `Password::defaults()` applies only when a password is changed or reset in production, not to a password set by a seeder or by hand.

**Attack path:**

1. The attacker learns or guesses the admin's login email.
2. They post password guesses to `/admin/connexion`, 5 per source address per minute, from rotating addresses.
3. A correct guess logs them in (or leads to the 2FA challenge, see F-02).

**Evidence:**

```php
return Str::transliterate(Str::lower($request->input(Fortify::username())).'|'.$request->ip());
```

**Impact:** Unlimited online password guessing against the admin account. Each failure on a known account also writes a `login_events` row, kept for a year.

**Remediation:** Define a `login` limiter with two keys and name it in `config/fortify.php` (`'limiters' => ['login' => 'login']`), then add `->middleware('throttle:login')` to the `login.store` route, since Fortify's own routes are ignored here:

```php
RateLimiter::for('login', fn (Request $request): array => [
    Limit::perMinute(5)->by(Str::lower((string) $request->input('email')).'|'.$request->ip()),
    Limit::perHour(30)->by('login-account|'.Str::lower((string) $request->input('email'))),
]);
```

Consider making 2FA mandatory for the account. Regression test: 31 failures for one email from 31 addresses, the last one refused.

**References:** CWE-307, OWASP Top 10 A07, OWASP ASVS V6.3, [Fortify authentication throttling](https://laravel.com/docs/13.x/fortify#login-throttling).

### F-04: Subscription is confirmed, and cancelled, by a plain GET request

**Severity:** Low, CVSS 3.7 (`CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N`)

**Location:** `app/Http/Controllers/SubscriptionController.php:39-56` (`confirm()`), `:62-77` (`unsubscribe()`), `routes/web.php:55-60`.

**Description:** Opening the signed link is enough to confirm a subscription or to unsubscribe. Mail security gateways and link preview services open every link in incoming mail, so they do both without the person acting.

**Attack path:**

1. The attacker submits `victim@company.example` to the subscription form.
2. The company's mail gateway fetches the « Confirmer mon abonnement » link to scan it.
3. `confirm()` sets `is_verified` and `verified_at`. The address now counts as confirmed, with the gateway's IP as `confirmed_ip`, and receives every newsletter.

The reverse also happens without an attacker: a gateway that fetches « Se désabonner » in a newsletter unsubscribes the reader.

**Evidence:**

```php
if ($found->status === SubscriptionStatus::Pending) {
    $found->update(['is_verified' => true, 'verified_at' => now(), 'confirmed_ip' => $request->ip()]);
```

**Impact:** Double opt-in no longer proves consent for addresses behind a scanning gateway, which weakens the GDPR record the `confirmed_ip` column is meant to give. Real subscribers can be unsubscribed silently.

**Remediation:** Make the GET request show a page with one button (« Confirmer mon abonnement », « Me désabonner ») that posts to the same signed URL, and change state only on POST. The RFC 8058 one-click POST from mail clients already works and stays as it is. Regression tests: GET on either link leaves the row unchanged; POST changes it.

**References:** CWE-650 (Trusting HTTP Permission Methods on the Server Side), RFC 9110 §9.2.1 (safe methods), RFC 8058, OWASP ASVS V4.

### F-05: No security headers are set

**Severity:** Low, CVSS 3.1 (`CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:N/I:L/A:N`)

**Location:** `bootstrap/app.php:18-33` (middleware stack), `resources/views/app.blade.php:1-25`. The only response header the application adds is `X-Robots-Tag` (`app/Http/Middleware/NoIndexHeader.php:24`).

**Description:** No response carries `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` or a frame restriction (`X-Frame-Options` or `frame-ancestors`). The repository has no production web server configuration that would add them.

**Attack path:** There is no direct exploit. The headers are the second line of defence: if the sanitizer or a dependency ever lets script through, no CSP limits what it can do; a first visit over `http://` can be intercepted before the redirect because HSTS is missing; and any site may frame the public pages and the login page.

**Evidence:** `grep -rni "Content-Security\|X-Frame\|Strict-Transport\|nosniff\|Referrer-Policy" app bootstrap config resources/views` returns nothing.

**Impact:** Less protection for every reader and for the admin if another defect appears. Framing of the logged-in admin panel is already limited by the `SameSite=Lax` session cookie, which is not sent to a cross-site frame.

**Remediation:** Add one middleware to the `web` group (or the same headers in the production Caddyfile):

- `Strict-Transport-Security: max-age=31536000; includeSubDomains` (production only).
- `X-Content-Type-Options: nosniff`.
- `Referrer-Policy: strict-origin-when-cross-origin`.
- `Content-Security-Policy` with at least `frame-ancestors 'self'` (the article preview panel frames the site itself), `base-uri 'self'`, `object-src 'none'`, `form-action 'self'`, `frame-src https://www.youtube.com https://www.youtube-nocookie.com`, and a `script-src` limited to `'self'`, a nonce for the inline Inertia and JSON-LD scripts (`Vite::useCspNonce()`), and `https://www.googletagmanager.com`. Start with `Content-Security-Policy-Report-Only`, since TinyMCE and GA4 need testing.
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`.

Regression test: a public page and an admin page each carry the headers.

**References:** CWE-693 (Protection Mechanism Failure), CWE-1021, OWASP Top 10 A05 Security Misconfiguration, OWASP ASVS V3.4, [OWASP Secure Headers Project](https://owasp.org/www-project-secure-headers/), [Laravel Vite CSP nonce](https://laravel.com/docs/13.x/vite#content-security-policy-csp-nonce).

### F-06: Password reset request answers faster for an unknown address

**Severity:** Low, CVSS 3.7 (`CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N`)

**Status:** Unconfirmed. The code path is certain; the timing gap was not measured, because local mail goes to Mailpit and the gap depends on the production SMTP relay.

**Location:** `app/Providers/FortifyServiceProvider.php:72-82` (`ResetPassword::toMailUsing`), `routes/admin.php:31-33` (`password.email`), `vendor/laravel/framework/src/Illuminate/Auth/Passwords/CanResetPassword.php:25-28`.

**Description:** `UniformPasswordResetLinkResponse` makes the page answer the same for a known and an unknown address. But Laravel's `ResetPassword` notification is not queued, so for a known address the request waits for the SMTP exchange with Brevo (to the login email and the recovery email), and for an unknown one it returns at once. Every other notification in the application is queued.

**Attack path:**

1. The attacker posts candidate addresses to `/admin/mot-de-passe-oublie` (5 a minute per IP).
2. A response several hundred milliseconds slower than the others marks the address that has an account.
3. That address is then the target for F-03 and for phishing.

**Evidence:**

```php
public function sendPasswordResetNotification(#[\SensitiveParameter] $token)
{
    $this->notify(new ResetPasswordNotification($token));
}
```

**Impact:** Discloses the admin's login email, which the uniform response was written to hide.

**Remediation:** Override `sendPasswordResetNotification()` on `User` to send a queued notification (a subclass of `ResetPassword` that implements `ShouldQueue`), so both cases return after one database write. Regression test: with `Notification::fake()`, assert the notification sent is an instance of `ShouldQueue`. To settle the status, time 20 requests for each case against a staging copy that uses the real relay.

**References:** CWE-208 (Observable Timing Discrepancy), CWE-204, OWASP ASVS V6.3 (consistent responses in credential recovery), OWASP Top 10 A07.

### F-07: No trusted proxy configuration: IP-based controls and signed links depend on the production topology

**Severity:** Low, CVSS 3.7 (`CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:L`)

**Status:** Unconfirmed. It depends on how production is deployed, which is not decided in the repository.

**Location:** `bootstrap/app.php:18-33` (no `trustProxies()` call), `app/Providers/AppServiceProvider.php:47` and `:93-97`, `app/Providers/FortifyServiceProvider.php:85` and `:97`, `app/Http/Controllers/SubscriptionController.php:43` and `:64`, `config/session.php:172`.

**Description:** Every throttle, the login history, the device list and `confirmed_ip` use `$request->ip()`, and no proxy is trusted. If FrankenPHP answers the internet directly, this is correct. If a load balancer, a CDN or a separate TLS proxy sits in front:

- Every visitor shares the proxy's address. The first 5 subscriptions of each hour use up the limit for everyone, and login throttling is shared too.
- The application sees `http`. `hasValidSignature()` compares the request URL with links signed as `https://` (`URL::forceScheme('https')`), so confirmation, unsubscribe and email-change links all fail.
- `SESSION_SECURE_COOKIE` is unset, so the session cookie gets the `Secure` flag only when the application sees `https`.

The opposite mistake, trusting every proxy (`trustProxies(at: '*')`) while the application port is reachable directly, would let a client forge `X-Forwarded-For` and escape all throttles.

**Attack path:** In the proxied case, an attacker sends 5 subscription requests an hour and the form refuses every real visitor (« Trop de tentatives. Réessayez dans une heure. »).

**Evidence:** `grep -rn "trustProxies\|TrustProxies" bootstrap app config` returns nothing.

**Impact:** Depending on the topology: either none, or a trivial denial of the subscription form, broken email links, and a session cookie without `Secure`.

**Remediation:** Decide the topology in the production setup session, then, if there is a proxy, add `$middleware->trustProxies(at: [<proxy addresses>])` with the exact addresses, never `*` unless the application port is closed to the internet. Set `SESSION_SECURE_COOKIE=true` in production in every case. Add a deployment check: a signed confirmation link opened through the public URL answers 200, and `$request->ip()` logged for a test request is the client's address.

**References:** CWE-348 (Use of Less Trusted Source), CWE-614, OWASP Top 10 A05, [Laravel trusted proxies](https://laravel.com/docs/13.x/requests#configuring-trusted-proxies).

### F-08: `/recherche?q[]=` returns a 500 error

**Severity:** Informational (no CVSS score: no confidentiality, integrity or availability impact)

**Location:** `app/Http/Controllers/SearchController.php:36` (`__invoke`).

**Description:** `$request->string('q')` converts the input to a string. When `q` is sent as an array, PHP raises "Array to string conversion", which Laravel turns into an exception and a 500 response.

**Attack path:** Anyone requests `GET /recherche?q[]=a`.

**Evidence:** Local test: `AUDIT search q[]: 500`. For comparison, `/?page[]=a` and `/recherche?q=a&page[]=1` both answered 200.

**Impact:** No data is exposed when `APP_DEBUG` is false. Each request writes a stack trace to the log, so the endpoint can fill it, and error monitoring gets noise.

**Remediation:** Read the value defensively, as the form requests already do: `$raw = $request->query('q'); $query = is_string($raw) ? Str::of($raw)->squish()->limit(...)->toString() : '';`. The same pattern (`$request->string('q')`) is in the admin list controllers, where only an authenticated user can trigger it. Regression test: `GET /recherche?q[]=a` redirects to the home page like an empty query.

**References:** CWE-755 (Improper Handling of Exceptional Conditions), CWE-20, OWASP ASVS V2.2 (input validation).

### F-09: The sanitizer keeps `id` on every element and any `allow` value on iframes

**Severity:** Informational (no exploit path was found)

**Location:** `app/Support/ArticleHtml.php:284` (`allowAttribute('id', '*')`), `:275` (`iframe` with `allow`).

**Description:** Article, chapô, biography and newsletter HTML may carry any `id`. In a browser, an element with an `id` becomes a property of `window` (DOM clobbering), and it can duplicate an `id` the page uses. YouTube iframes also keep whatever `allow` value the content gives, such as `camera; microphone; geolocation`.

**Attack path:** Only an administrator can write this HTML. An article containing `<a id="dataLayer"></a>` makes `window.dataLayer` an element before `loadGoogleAnalytics()` runs (`resources/js/lib/google-analytics.ts:22`), so `dataLayer.push` fails and the page is not measured. No path to script execution was found: the application reads no other global by name, and `document.getElementById` returns the page's own element first.

**Evidence:** Sanitizer output for `<a id="dataLayer"></a>` is `<a id="dataLayer"></a>`, and for a YouTube iframe with `allow="camera; microphone; geolocation"` the attribute is kept unchanged.

**Impact:** None today beyond a broken analytics tag on one page. It is a latent risk if later code reads `window.<name>` or looks elements up by `id`.

**Remediation:** In the DOM pass, prefix content ids (`id="c-…"` and the matching `aria-describedby` and `href="#…"` values), or drop any `id` that is not a simple slug and is in a deny list of page ids. Replace the iframe `allow` value with the fixed list YouTube needs (`accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share`), and add `referrerpolicy="strict-origin-when-cross-origin"`. Regression tests in `ArticleHtmlTest`: `id="dataLayer"` does not survive unchanged; an iframe `allow` with `camera` is rewritten.

**References:** CWE-1021, CWE-79 (related, DOM clobbering), [OWASP DOM Clobbering Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/DOM_Clobbering_Prevention_Cheat_Sheet.html).

## 7. Checked with no issues found

- **Routes:** all 82 routes were listed. Every `admin.*` panel route is behind `EnsureAdminIsAuthenticated` and `auth.session`; the four guest pages are behind `guest`; the two unauthenticated admin links check a signature and a hash; logout requires a session.
- **Authorization and IDOR:** the application has one role and no per-user resources. Account actions always act on `$request->user()`, and device logout matches a keyed hash against the user's own sessions.
- **Mass assignment:** every model declares `#[Fillable]`, no `Model::unguard`, controllers fill from named, validated fields, and `forceFill` is used only with fixed keys.
- **SQL:** every raw fragment (`whereRaw`, `selectRaw`, `orderByRaw`, `DB::raw`) uses bound parameters or constants. Sort columns come from an allowlist (`CategoryController`). `ILIKE` searches escape `%`, `_` and `\`.
- **Public search:** the query is bound into `websearch_to_tsquery`, cut to 200 characters and paginated by 10. Highlights reach the page as text segments, and React renders the `<mark>` elements, so no HTML from the database or the query is injected.
- **Article HTML pipeline:** 48 payloads (script, event handlers, `javascript:` and `data:` URLs with entity and whitespace tricks, SVG, MathML, `style`, `noscript`, `template`, `select`, raw-text elements, comments, `base`, `meta`, `srcset`, `srcdoc`, backslash and userinfo host tricks on `iframe`, `video` and `source`, attribute breakouts through `alt` and `caption`) produced no executable output from `sanitize()` or `clean()`. Content is sanitized on save and again on every render, feed, Markdown export and newsletter.
- **Frontend sinks:** the six `dangerouslySetInnerHTML` uses take sanitized HTML, the Fortify QR code SVG, or JSON-LD encoded with `JSON_HEX_TAG`. Newsletter previews render in `sandbox=""` iframes. No `postMessage` handler, `eval` or dynamic `href` from user input exists. External links carry `rel="noopener noreferrer"`.
- **Inertia props:** public pages expose only article, category and author display fields. Shared props give `auth.user` as `id` and `avatar` only. No email, token or config secret is serialized to a public page.
- **Open redirects:** `CanonicalUrl`, the V1 profile redirect and the slug redirects all build their target from `APP_URL` or a named route.
- **Subscription tokens:** links are HMAC-SHA256 signed URLs keyed by `APP_KEY`, compared in constant time by the framework. The confirmation link expires after 48 hours and stops working after an unsubscribe. The form answers the same for known and unknown addresses. Emails are lowercased, validated with `email:rfc` (no header injection) and checked against the disposable list including parent domains.
- **Brevo webhook:** 404 when no token is configured, 401 without the token, `hash_equals` comparison, 120 requests a minute, and only three event types change data.
- **Newsletter email:** the subject, preheader, card fields and unsubscribe URL are escaped; the body goes through `ArticleHtml::clean()`; `List-Unsubscribe` and `List-Unsubscribe-Post` are set.
- **Cookie consent and GA4:** the tag loads only when the consent cookie says `granted` (`cookie-consent.tsx:40`), never on admin pages (measurement ID is `null` there), and refusal sets `ga-disable-*` and clears the `_ga` cookies. The consent cookie is `SameSite=Lax` and `Secure` on HTTPS; it cannot be `HttpOnly` because the script must read it.
- **Authentication and session:** password, email, recovery email, recovery phone, 2FA enable, disable and recovery code actions all require the current password, so a stolen session cannot take over the account. Password change and reset invalidate other sessions and the remember token. The session cookie is `HttpOnly` and `SameSite=Lax`. The password reset request and its form are throttled and answer uniformly. Guests get a 404 on the panel.
- **CSRF:** `PreventRequestForgery` covers every state-changing route. The two exemptions are the signed unsubscribe URL and the token-authenticated webhook. Same-site requests are not exempted (`$allowSameSite` is false).
- **Uploads:** covers, avatars and editor images are validated with `image` and `mimes` (no SVG), size-limited, and sent to Cloudinary; nothing is stored on the local or public disk, and the client filename never reaches a path or a response header.
- **Outbound requests (SSRF):** every outbound call goes to a fixed host (Cloudinary, Google, Gemini, IndexNow, GitHub raw for the disposable list). No user-supplied URL is fetched. Cloudinary deletion checks the cloud name first.
- **Local file serving:** the framework's `/storage/{path}` route serves the private local disk only with a valid signed URL, and the directory is empty.
- **Debug and dev tooling:** `config/app.php` defaults `APP_DEBUG` to false and `APP_ENV` to production. Inertia DevTools routes are active only in the `local` environment unless `INERTIA_DEVTOOLS_ENABLED` is set.
- **Secrets:** `.env` and `.mcp.json` are ignored and were never committed. All 57 commits were searched for AWS, Google, Brevo, GitHub and Cloudinary key formats, private keys and `APP_KEY` values: the only matches are fake Cloudinary credentials in tests (`<redacted: placeholder Cloudinary URL, tests/Feature/Admin/*Test.php>`) and the GA4 measurement ID in `.env.example`, which is public by nature. `docker-compose.yml`, `.env.example` and the CI workflow use a development-only database password (`<redacted: local database password, .env.example and .github/workflows/tests.yml>`).
- **Error pages:** 404 pages render the public not-found page, expired admin forms redirect with a message, and no response path echoes exception text. Upstream errors (Cloudinary, Gemini, GA4) are logged and replaced by fixed French messages.
- **Denial of service:** every public list is paginated or capped; the sitemap, feed and llms files are cached for 15 minutes; no public endpoint accepts a page size.
- **Octane:** no request data is kept in static properties or singletons. The static sanitizer instances and the `Cloudinary` singleton hold configuration only.

## 8. Not verified

- **Production configuration:** `APP_DEBUG`, `APP_ENV`, `APP_KEY` rotation, `SESSION_SECURE_COOKIE`, `LOG_LEVEL`, file permissions, and whether `storage/`, `.env` or `public/hot` are reachable. No production environment is described in the repository. A review of the production `.env` and web server configuration would settle it.
- **TLS and headers at the edge:** certificate, protocol versions, HTTP to HTTPS redirect and any header added by the server. Settle with an external scan (for example Mozilla Observatory and SSL Labs) once the site is deployed, with the owner's agreement.
- **F-06 timing gap** and the **DNS lookup duration in F-01:** both need measurements against a staging copy with the real mail relay and resolver.
- **F-07:** needs the production topology.
- **Timing difference on the subscription form** between a confirmed address (returns before any write) and a new one (one insert and one queued job): expected to be a few milliseconds and not measured.
- **Third-party account settings:** Cloudinary (signed uploads only, no unsigned preset), Brevo (webhook authentication, sender domain SPF, DKIM and DMARC), the Google service account scope, and the Gemini key restrictions. They need access to those consoles.
- **V1 data already in the database:** stored covers and avatars are trusted URLs, and old article HTML is sanitized on render, but the rows themselves were not inspected.
- **Vite advisories:** not matched by the tools because of the Vite+ alias (see section 6).
