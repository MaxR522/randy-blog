# Deployment analysis (2026-11-14)

Review of the existing V1 deployment (`/home/mario/Projects/deploy-personal-blog`, private repository `MaxR522/deploy-personal-blog`) before V2 goes to production, and the recommended continuous delivery setup for V2 and the other site on the same host (Mémoire du monde, `unesco`).

Goals set by the user:

- Automated delivery like V1: push fixes, the pipeline passes, the new image is deployed and the running container restarted, without manual steps.
- Zero downtime on updates, or the least downtime possible.
- The same setup must later fit Mémoire du monde, which will be refactored.

## 1. Current setup

One Docker Compose file on the host runs:

- Traefik v3.6: TLS through Let's Encrypt (TLS challenge), HTTP → HTTPS, `www` → apex 301 for the blog.
- Postgres 16 (`db`).
- V1 blog (`blog`, image `maxr522/personal-blog:latest` from Docker Hub, port 8000).
- Mémoire du monde (`unesco`, built on the host from `/home/mario/unesco`, port 8000).
- Watchtower: polls Docker Hub every 60 s and restarts containers labelled `com.centurylinklabs.watchtower.enable=true` when `latest` changes.

V1 workflow: push fixes, create a tag, CI builds the image and pushes `latest`, Watchtower pulls it and restarts the container.

The overall shape (one host, Compose, Traefik routing by labels, one container per app) is sound and is kept. The update mechanism and several details are not.

## 2. Why Watchtower stopped working

The cause is not Ubuntu but Docker Engine 29 (November 2025), which raised the minimum API version it accepts to 1.44. `containrrr/watchtower` negotiates API 1.25 and fails with `client version 1.25 is too old`. The project is effectively abandoned (last release in 2023).

Workarounds exist (`DOCKER_API_VERSION=1.44` on the Watchtower container, or a maintained fork such as `nicholas-fedor/watchtower`), but going back to Watchtower is not recommended:

- Downtime on every update. Watchtower stops the old container, then starts the new one. With a single replica, `--rolling-restart` does not help: the site is down for the Octane boot plus `migrate --force`.
- No feedback. CI is green, but whether the deploy worked is only visible on the server; a failed pull or a crash loop is silent.
- `latest` hides which version runs. Rollback means re-tagging images by hand on Docker Hub.

## 3. Problems found in the deploy repository

- Secrets in git: `config.json` (Docker Hub credentials mounted by Watchtower) is committed, and `.env.example` carries a real `APP_KEY`. Remove both from the repository and rotate the Docker Hub token, even though the repository is private.
- Postgres publishes `5432:5432` on the host. Drop the port mapping: the apps reach `db` on the Compose network, and dumps go through `docker exec`.
- Anonymous volumes hide new code. `blog` mounts an anonymous volume on `/var/www/html/public` and `unesco` on `/var/www/html`. Compose keeps anonymous volumes when it recreates a container, so a new image can keep serving the old files; for `unesco` that is the whole application. Drop them: the code and built assets ship in the image.
- `deploy.replicas` and `update_config` are Docker Swarm keys; plain Compose ignores them.
- The `blog` service lists every environment variable one by one, so V2's new variables would be missing. Switch to `env_file`.
- V1 paths do not fit V2: healthcheck on `/health` (V2: `/up`), storage volume on `/var/www/html/storage` (V2 image: `/app`).
- Loose ends: the README is stale (it describes `*.txt` secret files that are no longer used), `conf/fail2ban.yml` is not wired into Traefik (no plugin loaded), the Traefik rate limit is commented out, `/var/log/traefik` has no rotation, and the `www` redirect regex leaves its dots unescaped.

Most of these are already listed in session 15 of `docs/admin-roadmap.md`.

## 4. Recommendation: GitHub Actions deploys over SSH, `docker rollout` for zero downtime

Keep Compose and Traefik, remove Watchtower, and let CI push the deploy instead of the server polling for it.

### Flow

On a `v*` tag:

1. The `tests` job passes.
2. A `build` job builds the production image and pushes `maxr522/personal-blog:v2.0.3` (plus `latest`, optional).
3. A `deploy` job connects over SSH and runs `deploy.sh blog v2.0.3` on the host.

The deploy result (success, failed migration, failed healthcheck) shows up in the GitHub Actions run.

### Deploy script

`deploy.sh` lives in the deploy repository and is generic, so every app uses it:

```bash
#!/usr/bin/env bash
set -euo pipefail
app="$1"; tag="$2"
[[ "$tag" =~ ^v[0-9]+\.[0-9]+\.[0-9]+$ ]] || { echo "bad tag"; exit 1; }
cd /home/mario/deploy-personal-blog
sed -i "s/^${app^^}_TAG=.*/${app^^}_TAG=${tag}/" .env   # BLOG_TAG=v2.0.3
docker compose pull "$app" "$app-queue" "$app-scheduler"
docker compose run --rm "$app" php artisan migrate --force   # once, not per container
docker rollout "$app"                                        # zero-downtime swap
docker compose up -d "$app-queue" "$app-scheduler"           # a short restart is fine for workers
```

The compose file pins the image to the version: `image: maxr522/personal-blog:${BLOG_TAG}`. What runs in production is always known from `.env`.

Rollback: `deploy.sh blog v2.0.2`, from the host or by re-running an older Actions run. Migrations do not roll back, see the rules below.

### Zero downtime

[`docker rollout`](https://github.com/Wowu/docker-rollout) is a single-file Docker CLI plugin (installed into `~/.docker/cli-plugins/`). It scales the service to two containers, waits for the new one's healthcheck to pass, lets Traefik send traffic to both, then drains and removes the old container (draining since v0.12).

Requirements on the service:

- No `container_name`.
- No host `ports` (Traefik reaches it on the Compose network).
- A `healthcheck` (V2: `/up`).

Traefik routes by labels, so it picks up the second container with no configuration change.

### Rules that come with it

- Migrations run once, in `deploy.sh`, before the swap, not in the container's start script: during the overlap two containers would both migrate.
- Migrations must stay compatible with the previous release's code for the few seconds of overlap (expand, then contract in a later release: add a column first, drop the old one later). The V1 → V2 cutover is the exception, since it is a planned maintenance window anyway.
- The queue worker and the scheduler do not need a zero-downtime swap: `queue:work` finishes its current job on `SIGTERM`, give the service a `stop_grace_period` longer than the longest job.

### SSH access

- A dedicated `deploy` user on the host and a deploy-only SSH key stored as a GitHub Actions secret, with the host key pinned in `known_hosts`.
- The key is restricted in `authorized_keys` with `command="…/deploy-wrapper",no-pty,no-port-forwarding,no-agent-forwarding`: the wrapper reads `$SSH_ORIGINAL_COMMAND`, accepts only `<app> <tag>` with a known app name and a `vX.Y.Z` tag, and calls `deploy.sh`.
- Membership in the `docker` group is equivalent to root on the host, so the forced command is the real protection; the key must not allow a shell.

## 5. Fit for Mémoire du monde

The same script, compose layout and Actions workflow apply. When it is refactored:

- Build its image in its own CI and push it to a registry, instead of `build:` on the host.
- Remove the anonymous `/var/www/html` volume.
- Add a healthcheck endpoint and the `UNESCO_TAG` variable, then deploy with `deploy.sh unesco vX.Y.Z`.

Caveat: it uses SQLite on a volume (`unescoDb`). Two containers sharing the file for a few seconds is fine, but the migration compatibility rule applies there too. Until the refactor it keeps running as it is; removing Watchtower does not affect it, since it is not labelled for Watchtower.

## 6. Alternatives considered

- Kamal: zero-downtime deploys built in (kamal-proxy), but it replaces Traefik and Compose and expects to manage the whole host. Too much change with two apps sharing one box.
- Single-node Docker Swarm: native `start-first` rolling updates and automatic rollback, but it changes Traefik's provider, does not support `build:`, and has its own behaviour for `env_file` and volumes. More moving parts than one plugin.
- Watchtower fork with `DOCKER_API_VERSION`: the smallest change, but no zero downtime and no deploy feedback.
- GitHub Container Registry instead of Docker Hub: optional. CI pushes with `GITHUB_TOKEN` (no Docker Hub token in CI) and Docker Hub's pull limits go away; the host needs a read-only token to pull. Not required for this setup.

## 7. Impact on the roadmap (session 15)

- CD box: becomes « build, push the version tag, deploy over SSH with `deploy.sh` and `docker rollout` » instead of « push `latest` for Watchtower ».
- Start script box: `migrate --force` moves out of the container start into `deploy.sh`.
- Deploy repository box: remove the Watchtower service and `config.json`, add `deploy.sh`, the SSH wrapper, `BLOG_TAG` in `.env.example`, and document deploy and rollback in the README.
